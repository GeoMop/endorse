# PLAN

## Goal

Study the distribution of the homogenized conductivity tensor field generated by uncertain DFN and material
parameters. The application is independent of `chodby_trans`; there is no transport solve and no fine/coarse tensor
pair.

Use the MLMC library as a single-level Monte Carlo scheduler through its paired-sampling path. Preserve similar
interfaces to `chodby_trans` where functionality is equivalent, allowing stable common parts to move into
`src/endorse` after both applications demonstrate their requirements.

## Stage A - deterministic homogenization problem

1. Keep test mesh construction in `create_mesh.py` and the three-load calculation in `problem.py`.
2. Build a microscale box with several conductivity regions and a fracture network.
3. Build one deterministic homogenization mesh whose element ordering defines the output field layout.
4. Use the six-component tensor returned by the current `macro_flow_model` calculation as the authoritative
   representation. Preserve component positions as numeric coordinates `1..6`.
5. Return `conductivity(el_id,tensor_comp)`, `el_barycenter(el_id,xyz)`, and `gmsh_id(el_id)`.
6. Validate consistent element counts, six tensor components, three barycentre coordinates, finite values, and unique
   Gmsh element ids.
7. Keep this implementation independent of the Chodby coarse-transport path. Equivalent low-level calls may remain
   similar so later comparison can identify a suitable common API.
8. Cover mesh persistence, stable homogenization element identity, result shape, and the three-load calculation with
   a focused integration test.

Completed: `create_study_meshes` and `run_homogenization_problem` are implemented; the deterministic integration
test remains pending a configured Flow123d run.

Stage A implementation steps:

1. Load the completed micro and homogenization meshes in `problem.py`.
2. Select the homogenization-mesh bulk elements and build the averaging subproblems used by the three-load solve.
3. Run the configured coverage preflight before any Flow123d calculation and expose the prepared state to the test.
4. Keep the micro-mesh conductivity field and Flow123d execution as the remaining USER work.

Current Stage B implementation steps:

1. Use one `HomogenizationSimulation` MLMC level with deterministic grouped parameter planning.
2. Build the fixed homogenization mesh once and create a sample-specific micro mesh in each worker workspace.
3. Persist conductivity fields and diagnostics in one level-free Zarr store with stable element geometry.
4. Resume unfinished samples through the MLMC HDF schedule and Dask sampling pool.
5. Keep a deterministic `RandomSimulation` and PBS `submit` command for validating the sampling infrastructure
   before running Flow123d.

## Stage B - single-level Monte Carlo sampling

1. Copy and adapt only the required parameter-transformation, reproducible sampling, Dask, PBS, HDF restart, and
   unfinished-sample resubmission behavior from `chodby_trans`.
2. Add `HomogenizationSimulation` with one MLMC level. Return the conductivity field as the fine value and the
   MLMC-required zero coarse value.
3. Do not expose a level dimension in scientific Zarr storage.
4. Use coordinates `sample_id`, `el_id`, `parameter`, `tensor_comp=1..6`, and `xyz=[x,y,z]`.
5. Store `conductivity(sample_id,el_id,tensor_comp)`, `el_barycenter(el_id,xyz)`,
   `param_val(sample_id,parameter)`, `return_code(sample_id)`, `eval_time(sample_id)`, and `gmsh_id(el_id)`.
6. Create the homogenization mesh once per run and require identical element ids and barycentres for every sample.
7. Cover deterministic planning, sample workspaces, concurrent Zarr writes, failures, restart, and local Dask before
   the first MetaCentrum run.

## Generalization policy

- Keep copied behavior recognizably parallel to its `chodby_trans` source while the two applications are evolving.
- Remove transport-specific branches, names, configuration, quantities, and storage dimensions from this package.
- Move code into `src/endorse` only after both applications use the same stable contract.
- Keep application-specific configuration, result schemas, and physical orchestration in their owning application.
